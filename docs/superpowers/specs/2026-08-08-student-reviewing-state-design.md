# 学生节点等待审核状态设计

## 1. 目标

优化学生提交节点后的等待审核界面，使学生能够明确确认：材料已经提交、系统正在审核、提交时间和本次提交内容均已记录。

本次仅调整节点弹窗中 `reviewing` 与 `submitted` 状态的前端展示，并让现有轮询同时覆盖这两个等待状态；不修改审核流程、2 秒轮询频率、后端接口、数据库或状态机。

## 2. 当前问题

当前节点进入 `reviewing` 或 `submitted` 后，弹窗只显示“自动审核中”和“材料已提交，正在等待审核”两处简单文字，存在以下问题：

- 状态层级弱，用户不易确认提交是否真正完成；
- 未展示提交时间；
- 未展示本次已提交内容，用户无法核对文件或表单；
- 审核等待与普通不可操作状态的视觉差异不足。

现有运行时数据已经提供 `submission`、`submittedAt` 和可选的 `audit.attemptCount`，无需新增数据字段。

## 3. 页面结构

当 `runtime.status` 为 `reviewing` 或 `submitted` 时，节点弹窗主体使用专用等待审核布局：

1. 保留现有节点弹窗标题区，包括状态、节点标题、说明和关闭按钮。
2. 显示审核状态卡：
   - 紫色浅底和紫色边框，延续现有 `reviewing` 状态语义；
   - 使用纯 CSS 轻量旋转图标；
   - 主标题为“材料已提交，正在自动审核”；
   - 元信息显示“第 N 次审核 · 提交于 <时间>”；
   - 辅助说明为“审核结果会自动刷新，你可以先关闭此窗口处理其他事项。”
3. 在状态卡下显示“本次提交内容”的只读摘要。

不显示百分比、模拟进度条或预计完成时间，因为当前系统没有可证明的审核进度与完成时长。

## 4. 数据与组件复用

等待审核布局只读取现有运行时数据：

- 审核次数：优先使用 `runtime.audit?.attemptCount`，无记录时按第 1 次显示；
- 提交时间：使用 `runtime.submittedAt` 和现有 `formatDateTime()`；
- 提交内容：使用 `runtime.submission`；
- 节点类型：使用现有 `node.kind`。

提交内容复用现有 `ReadonlySubmission`：

- 文件节点展示文件名、文件大小和提交时间；
- 表单节点展示字段与答案；
- 确认或公告节点展示确认状态。

不复制只读展示逻辑，不新增独立组件目录或第三方依赖。可在 `StudentRuntimePage.tsx` 内增加一个只负责等待审核布局的轻量函数组件，使 `RuntimeNodeDialog` 的条件分支保持清晰。

## 5. 状态与交互规则

- `reviewing` 与 `submitted` 共用同一等待审核布局。
- 等待期间不提供修改、暂存、重复提交或手动刷新按钮。
- 用户可以通过现有右上角关闭按钮或弹窗遮罩关闭节点窗口。
- 关闭节点窗口不停止页面级自动刷新。
- 现有每 2 秒审核状态轮询频率保持不变，轮询条件由仅识别 `reviewing` 扩展为识别 `reviewing` 或 `submitted`。
- 审核通过后，现有状态更新自动切换为完成页面。
- 审核退回后，现有状态更新自动切换为可修改页面。
- 审核异常后，现有状态更新进入重新审核页面。
- 自动刷新暂时失败继续使用现有非阻塞页内提示，不改变节点状态，不显示为审核失败。

## 6. 异常数据边界

- `runtime.submittedAt` 缺失或无效时显示“提交时间暂未记录”，不得使用当前时间代替。
- `runtime.audit` 缺失或 `attemptCount` 小于 1 时显示“第 1 次审核”。
- `runtime.submission` 缺失字段时沿用 `ReadonlySubmission` 的“未记录”展示。
- `submitted` 尚未生成审核任务时仍显示等待审核布局，不要求存在 `runtime.audit`。

## 7. 视觉规范

- 使用现有项目字体、间距、圆角和色彩体系。
- 状态卡采用现有 `reviewing` 紫色语义，不引入新主题色。
- 旋转图标只使用 CSS，遵循 `prefers-reduced-motion`：用户偏好减少动画时停止旋转。
- 提交摘要继续使用现有灰白只读卡片样式。
- 小屏幕下状态元信息允许换行，不能横向溢出。

## 8. 文件范围

- Modify: `frontend/src/features/academic-flow/StudentRuntimePage.tsx`
- Modify: `frontend/src/styles.css`
- Create: `docs/superpowers/specs/2026-08-08-student-reviewing-state-design.md`

不修改后端、数据库、API 类型、学生拓扑节点或其他状态页面。前端轮询只扩展等待状态集合，不改变请求接口或时间间隔。

## 9. 验收标准

1. `reviewing` 和 `submitted` 节点打开后均显示专用等待审核状态卡。
2. 状态卡显示审核次数、真实提交时间和自动刷新说明。
3. 文件、表单、确认或公告节点均显示本次提交内容的只读摘要。
4. 等待期间没有修改、暂存、重复提交或手动刷新入口。
5. `reviewing` 与 `submitted` 均保持每 2 秒自动刷新；关闭节点弹窗后轮询继续，状态变化后重新打开可看到最新状态。
6. 审核通过、退回或异常后的既有页面逻辑不变。
7. 审核状态卡不显示无法证明的百分比、进度条或预计完成时间。
8. 缺失提交时间、审核次数或部分提交字段时使用明确降级文案，不出现空白或伪造数据。

## 10. 验证边界

按项目约定，不运行自动化测试、构建或浏览器测试。实施完成后进行静态业务审计：

- `reviewing` 和 `submitted` 是否进入同一专用分支；
- 页面轮询是否以相同 2 秒间隔覆盖 `reviewing` 和 `submitted`；
- 是否复用 `ReadonlySubmission`、`formatDateTime()` 和现有轮询；
- 是否没有新增修改或重复提交入口；
- 是否没有修改其他状态分支、后端、数据库或 API；
- CSS 动画是否支持 `prefers-reduced-motion`；
- 是否不存在无依据的进度与耗时信息。

完成静态审计后重启本地 FastAPI 与 Vite 服务，交由用户手动验收。
