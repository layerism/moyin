# 学生已上传文件下载与退回后重新上传设计

## 1. 目标

为学生文件节点补充已上传文件下载能力，并修正自动审核退回后的提交状态：上次已提交文件仍可下载核对，但不得直接再次提交；学生必须重新上传文件后才能重新提交节点。

## 2. 当前问题与根因

后端已经提供 `GET /api/student/files/{file_id}/download`，并校验文件所属学生及流程名单权限，但前端 API 和节点弹窗尚未使用该接口。

文件提交后，后端会把该文件绑定到本次 submission。审核退回时，页面轮询更新了节点状态，但当前组件生命周期内的前端本地 `draft.file` 仍保留上次提交的 `fileId`，导致界面误显示“文件已上传，可提交”并启用提交按钮。后端实际会拒绝这个已绑定文件，因此当前前后端状态表达不一致。

## 3. 方案

采用前端最小修正，复用现有下载接口和后端提交约束，不新增后端字段、接口或数据库结构。

前端同时识别两个文件来源：

- 当前待提交文件：`draft.file`；
- 上次已提交文件：`runtime.submission.file`。

当节点状态为 `rejected` 且两个 `fileId` 相同，或不存在新的 `draft.file` 时，视为“尚未重新上传”。旧文件只作为下载目标，不作为可提交文件。只有 `draft.file.fileId` 存在且不同于上次提交的 `fileId`，才视为新的待提交文件。

## 4. 下载规则

下载目标按以下优先级确定：

1. 存在新的待提交文件时，下载新文件；
2. 否则存在上次提交文件时，下载上次提交文件；
3. 两者均不存在时，不显示下载按钮。

前端 API 增加 `downloadNodeFile(fileId)`，调用现有学生文件下载接口。成功后使用接口返回的签名 URL 和原文件名触发浏览器下载；失败时复用现有“操作未完成”提示弹窗。

下载按钮放在文件选择标签之外，避免点击下载时同时触发文件选择器。按钮文案根据目标显示为“下载已上传文件”或“下载上次提交文件”。下载期间禁用重复点击，但不改变文件状态。

## 5. 退回后的上传与提交规则

文件节点处于 `rejected` 且尚未重新上传时：

- 上传工作区显示“审核未通过，请重新上传文件”；
- 展示上次提交文件的名称与大小，供学生核对；
- 提供“下载上次提交文件”；
- “提交节点”保持禁用；
- 按钮下提示“请重新上传文件”。

重新上传成功后：

- 新文件替换为当前待提交文件；
- 上传工作区恢复“文件已上传，可提交”；
- 下载目标切换为新文件；
- “提交节点”恢复可用。

其他 `available`、`draft` 状态沿用现有规则：有待提交文件即可下载和提交，无文件时要求先上传。后端现有“已提交文件不能再次绑定”的校验继续作为最终一致性保护。

## 7. 异常边界

- 下载链接生成失败时保留当前上传和提交状态，只显示错误提示。
- 下载按钮在上传、下载或节点操作进行中禁用，避免重复请求。
- 缺少文件名或大小时沿用现有格式化降级，不伪造数据。
- 即使前端状态异常启用了旧文件提交，后端仍拒绝已绑定的 `fileId`。

## 8. 验收标准

1. 已上传文件的节点显示下载按钮，并能下载当前待提交文件。
2. 审核退回且未重新上传时，可下载上次提交文件，但提交按钮不可交互。
3. 退回后上传新文件，下载目标切换到新文件，提交按钮恢复可用。
4. 刷新页面和审核轮询状态切换后的规则一致，不依赖仅存在于当前组件生命周期的临时状态。
5. 下载失败不会清除文件、改变节点状态或错误启用提交按钮。
6. 不新增后端接口、数据库字段或第三方依赖。

## 9. 验证边界

依据项目约定，实施阶段不运行自动化测试、构建或浏览器测试，仅进行静态业务逻辑审计：

- 下载目标是否严格遵循“新文件优先，否则上次提交文件”；
- `rejected` 状态是否要求新 `fileId` 与上次提交 `fileId` 不同；
- 下载按钮是否位于文件选择标签之外；
- 提交按钮、提示文案与后端现有文件绑定约束是否一致；
- 是否仅修改约定的前端文件并复用现有接口。

完成静态审计后重启本地 FastAPI 与 Vite 服务，由用户在学生流程页面手动验收。
