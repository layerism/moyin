# 扫描件文件选择上传修复设计

## 1. 问题与目标

确认承诺节点的扫描件工作区通过文件选择器选中文件后，没有发出上传请求；拖拽上传不受影响。目标是恢复文件选择器的单文件和多文件上传，同时保持现有接口、校验、提示与拖拽行为不变。

根因位于 `ScanUploadWorkspace`：事件处理器保存浏览器提供的实时 `FileList` 后，先将文件输入框的 `value` 清空，再读取 `FileList.length`。清空输入框会同步清空该 `FileList`，因此上传函数不会执行。

## 2. 方案

在清空文件输入框前，使用 `Array.from()` 将选中的文件复制为独立的 `File[]`；随后清空输入框，并把复制后的数组交给现有 `upload()`。

不采用以下方案：

- 只复制第一个 `File`：会破坏当前扫描件多选能力；
- 上传结束后再清空输入框：会改变重复选择同名文件的交互，并增加异步状态耦合；
- 修改后端接口或预览鉴权：运行日志表明预览实例、模板下载和扫描件列表请求均已成功，故不属于故障边界。

## 3. 变更边界

仅修改 `frontend/src/features/academic-flow/ScanUploadWorkspace.tsx` 的文件选择 `onChange` 处理：

1. 将当前 `FileList` 快照为 `File[]`；
2. 清空输入框；
3. 数组非空时调用既有 `upload()`。

不修改扫描件拖拽、替换、删除、排序、后端上传 API、OSS 存储、学生预览令牌或业务校验。

## 4. 验收标准

- 文件选择器选择一个 JPG、PNG 或 PDF 后会调用既有扫描件上传 API；
- 一次选择多个合法文件时按现有顺序逐个上传；
- 取消选择时不发出请求；
- 选择后输入框仍被清空，允许再次选择同名文件；
- 拖拽上传和扫描件替换逻辑保持不变。

## 5. 验证边界

项目规范禁止代码功能改动过程中运行测试或使用浏览器插件。本次通过源代码数据流审计确认：传入 `upload()` 的参数已从实时 `FileList` 变为清空输入框不再影响的独立 `File[]`。交付时明确说明未运行自动化测试和浏览器回归。
