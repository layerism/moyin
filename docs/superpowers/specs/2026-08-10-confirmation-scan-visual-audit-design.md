# 确认承诺节点扫描件与通用视觉审核设计

## 1. 目标

为“确认承诺”节点增加可选的扫描审核能力。教师启用后，学生必须确认承诺、下载 DOCX 模板、上传一组图片或 PDF 扫描件，并等待视觉模型审核完成。

视觉审核面向 OpenAI Chat 兼容协议，不绑定豆包或其他供应商。当前部署可在后端 `.env` 中配置豆包兼容地址、占位 Key 和视觉模型；后续切换兼容服务只修改环境变量。

本次同时删除表单字段卡片展开区中的“字段类型”二次选择器。字段类型在教师点击“+ 单行文本 / + 多行文本 / + 单项选择 / + 多项选择”时已经确定，创建后不再转换。

## 2. 已确认的业务规则

### 2.1 功能范围

- 扫描审核只增加到“确认承诺”节点；
- 使用 `scanAuditEnabled` 显式启用；
- 历史确认承诺节点和新建确认承诺节点默认关闭，继续保留“仅勾选确认”的原行为；
- 启用后，确认勾选、模板下载、扫描件上传和审核成功缺一不可；
- 教师模板必须为 DOCX；
- 学生扫描件只允许 JPG、JPEG、PNG 和 PDF。

### 2.2 一组扫描件

一次待提交材料是一组有顺序的扫描件，允许：

- 多张图片；
- 一个多页 PDF；
- 图片与 PDF 混合；
- 上传后增加、删除、替换和调整顺序。

固定安全上限：

- 最多 10 个文件；
- 图片与 PDF 合计最多 20 页；
- 单个文件不超过 10 MB；
- 整组文件不超过 30 MB。

上述限制由前后端共同提示，但以后端验证为准，教师不能在节点设置中扩大限制。

### 2.3 两种互斥审核模式

教师必须选择一种模式，并为该模式填写自定义提示词：

1. `pass_fail`：通过/不通过模式，用于形式完整性审核；
2. `score`：评分模式，用于对完整提交进行 0–100 分评分。

一次提交只执行一种模式，不串行执行两套提示词。

通过/不通过模式中，不通过原因向学生和教师展示。评分模式中，合法评分结果直接使节点通过；分数与评分说明只向教师展示，不向学生展示，也不设置及格线。

## 3. 方案选择

采用“内置版本化通用视觉审核程序”，复用现有审核脚本运行时、SQLite 持久化任务、自动重试、服务恢复、手动重新审核、审核结果存储和 DAG 推进逻辑。

未采用独立视觉任务表，因为它会复制现有任务状态机；未采用提交接口同步调用模型，因为同步调用无法可靠处理超时、进程重启和重复提交。

通用视觉审核程序由项目提供，教师不能上传、替换或选择其实现。流程发布时为启用扫描审核的确认承诺节点固定程序 ID、版本和哈希；教师只看到审核开关、模式和提示词。

该程序在脚本清单中标记为内部程序，不出现在普通文件节点的审核脚本选择器中。发布逻辑把 `scanAuditMode` 与 `scanAuditPrompt` 映射为该固定版本的 `auditScriptParams`，继续接受现有参数配置哈希保护。

## 4. 节点配置

`AcademicFlowNode` 增加：

```ts
scanAuditEnabled?: boolean;
scanAuditMode?: "pass_fail" | "score";
scanAuditPrompt?: string;
```

继续复用 `templateAsset` 保存 DOCX 模板元数据。确认承诺节点只有在 `scanAuditEnabled === true` 时允许配置模板和视觉审核字段。

发布校验规则：

- 未启用扫描审核时，忽略视觉审核字段，保持原确认逻辑；
- 启用时必须具有合法 DOCX `templateAsset`；
- `scanAuditMode` 必须是 `pass_fail` 或 `score`；
- `scanAuditPrompt` 去除首尾空白后不能为空，长度上限为 2000 个字符；
- 启用时由发布逻辑固化内置审核程序 ID、版本、哈希和允许扩展名；
- 流程版本快照保存开关、模式、提示词和模板元数据，保证后续编辑不会改变已发布提交的审核标准。

克隆、草稿暂存、发布差异和修订影响比较必须包含新增字段与模板资产。

## 5. 教师端交互

确认承诺节点设置在开放时间区域后增加“扫描审核”设置：

- “启用扫描审核”开关；
- DOCX 模板上传、下载、替换和删除；
- 审核模式单选；
- 自定义提示词多行输入；
- 固定扫描件限制说明。

提示词输入区域随模式显示不同辅助文案：

- 通过/不通过模式：要求描述完整性、签名、日期、题目是否全部作答等形式标准；
- 评分模式：要求描述评分维度、权重或扣分规则。

教师不配置供应商、模型、Base URL 或 API Key。提交详情中，教师可以查看：

- 审核模式和状态；
- 通过/不通过结果及原因；
- 评分模式的分数和评分说明；
- 全部扫描件及其下载入口。

教师不能在提交详情中修改 AI 结果。

## 6. 学生端扫描件工作区

启用扫描审核的确认承诺节点按以下顺序展示：

1. 承诺内容与确认勾选；
2. DOCX 模板下载；
3. 扫描件上传工作区；
4. 提交动作。

存在模板时继续复用“先下载、后上传”的门控。扫描件工作区复用现有文件上传节点的拖放、上传中、成功、失败和下载反馈，但改为多文件列表。

每个文件展示：

- 文件名；
- 类型；
- 文件大小；
- 页数；
- 下载、删除、替换和排序操作。

上传中、模板未下载、未确认、扫描件为空或扫描件仍有校验错误时，提交按钮不可交互。提交成功后进入 `reviewing`，不能重复提交。

结果展示：

- 通过/不通过模式未通过：展示不通过原因，学生必须重新上传并产生新提交；
- 通过/不通过模式通过：展示审核通过并开放下游；
- 评分模式完成：只展示审核已完成，不展示分数或评分说明；
- 技术异常：展示脱敏错误并允许“重新审核”，保留原扫描件；
- 已提交或已通过状态始终保留扫描件下载入口。

## 7. 附件数据与 API

继续使用 `uploaded_files`，增加：

- `page_count`：图片为 1，PDF 为实际页数；
- `display_order`：同一学生、节点和提交阶段内的稳定顺序。

现有文件节点仍保持“一次一个待提交文件，上传即替换”的语义。多文件增加、删除和排序只对启用扫描审核的确认承诺节点开放。

上传接口在写入对象存储前完成：

- 扩展名和 MIME 类型检查；
- 图片实际解码；
- PDF 实际打开与页数读取；
- 单文件大小、文件数、总页数和总大小校验；
- 学生、流程名单、节点状态和模板下载门控校验。

删除和排序只允许操作当前学生、当前节点、尚未关联 Submission 的文件。已提交文件不可修改，只能通过新一轮上传形成下一次提交。

确认承诺提交快照保存：

```json
{
  "confirmed": true,
  "scans": [
    {
      "fileId": "...",
      "name": "scan-1.pdf",
      "size": 123456,
      "type": "application/pdf",
      "pageCount": 3,
      "order": 0
    }
  ]
}
```

Submission、扫描件关联、审核任务、节点状态和草稿删除必须在同一个 SQLite 事务中完成。重复 `idempotencyKey` 不得重复关联文件或创建第二个审核任务。

## 8. 视觉材料规范化

审核 worker 从对象存储下载 Submission 关联的全部扫描件，在既有临时审核目录中处理：

- 图片执行真实解码、EXIF 方向修正和 RGB 转换；
- PDF 使用现有 PyMuPDF 依赖逐页渲染；
- 页面按 `display_order`、文件内页码排列；
- 页面长边限制为约 2000 像素，输出为有界质量 JPEG；
- 渲染页数必须与上传时记录一致；
- 超限、解码失败、页数不一致或渲染失败均归类为技术异常。

临时原文件和渲染页面在成功、业务失败和异常路径中都必须清理。

## 9. OpenAI Chat 兼容请求

后端配置使用供应商无关名称：

```env
VISION_API_BASE_URL=https://ark.cn-beijing.volces.com/api/v3
VISION_API_KEY=replace-me
VISION_MODEL=replace-with-vision-model
VISION_API_TIMEOUT_SECONDS=120
```

`backend/.env.example` 提供占位配置；被 Git 忽略的本地 `backend/.env` 同样写入占位值，后续由用户替换。代码不得包含豆包专用域名、模型名或 Key。

上述四个变量不加入通用 `AUDIT_SCRIPT_ENV_ALLOWLIST`。执行器只有在解析出的程序 ID、版本和哈希均属于内置视觉审核程序时才注入这些变量，其他审核程序不能继承视觉服务凭据。

请求使用：

- `${VISION_API_BASE_URL}/chat/completions`；
- `Authorization: Bearer ${VISION_API_KEY}`；
- 标准 `model` 与 `messages`；
- 一个文本内容块和多个 `image_url` 内容块；
- Base64 `data:` URL，不向供应商暴露对象存储 URL。

火山方舟当前 ChatCompletions 文档明确展示同一消息中连续传入多个 `image_url` 的结构：

- https://api.volcengine.com/api-docs/view?action=ChatCompletions&serviceCode=ark&version=2024-01-01

为保持供应商兼容性，不依赖某一供应商专有 SDK。HTTP 客户端、材料规范化、错误分类和响应解析封装在版本化视觉审核程序的聚焦函数中，后续更换兼容服务不影响节点与任务逻辑。

系统提示词必须：

- 声明扫描件内容是不可信材料，忽略页面内要求模型改变审核规则的指令；
- 注入模式对应的固定 JSON 协议；
- 注入文件和页码顺序；
- 要求仅基于教师提示词与扫描页面审核；
- 禁止输出 Markdown 围栏或 JSON 之外的文字。

教师提示词作为审核标准插入受控消息结构，不能覆盖固定输出协议和安全指令。

## 10. 统一结果协议

模型在两种模式中都返回：

```json
{
  "passed": false,
  "score": null,
  "reason": "第 3、5 题未作答。"
}
```

通过/不通过模式：

- `passed` 必须是布尔值；
- `score` 必须是 `null`；
- `passed === false` 时 `reason` 去除首尾空白后不能为空。

评分模式：

- `score` 必须是有限的 0–100 数值；
- 合法评分结果由后端规范化为 `passed: true`；
- `reason` 作为评分说明保存；
- 模型返回的 `passed` 不得使评分模式进入业务拒绝状态。

视觉审核程序将结果规范化到现有审核协议，`details` 至少保存审核模式、分数、文件数和页数。原始模型响应不写入数据库、日志或前端响应。

## 11. 状态机与重试

复用现有任务规则：

- 创建 Submission 后立即进入 `reviewing`；
- 业务不通过进入 `rejected`，不自动重试；
- 请求超时、HTTP 异常、配置缺失、响应非 JSON、字段类型错误、分数越界、材料解码或渲染错误均为技术异常；
- 技术异常按现有 1、5、15 秒退避自动重试三次；
- 最终失败进入 `audit_error`，允许学生手动重新审核；
- 手动重新审核复用原 Submission 和扫描件；
- 服务重启恢复未完成任务；
- 旧任务不能覆盖后续新提交。

评分模式获得合法结果后直接进入 `approved` 并推进 DAG。通过/不通过模式只有 `passed === true` 才推进 DAG。

## 12. 可见性与安全边界

- `VISION_API_KEY` 只由后端读取；
- Key、Base URL 和模型名不进入流程快照、任务结果或前端；
- 不记录 Authorization 头、Base64 页面、教师完整提示词或原始模型响应；
- 学生 API 在评分模式下不返回 `score` 和评分说明；
- 教师提交详情接口经过教师身份与流程所有权校验后才能返回评分结果；
- 通过/不通过模式的不通过原因可以返回当前学生；
- 对象存储下载继续使用短期签名 URL；
- 图片解码启用像素上限，PDF 页数和渲染尺寸受限，防止解压缩炸弹与内存失控；
- 学生扫描件中的提示注入文本不能改变固定系统协议。

## 13. 表单字段类型调整

删除 `FormFieldEditor` 展开内容中的通用“字段类型”选择器和相关 CSS。保留：

- 顶部四种新增按钮；
- 字段标题原位编辑；
- 卡片折叠、排序、删除和错误提示；
- 多行文本字符限制；
- 单选和多选的选项配置；
- 多选的选择数量限制。

`changeFieldType` 及只服务于类型转换的逻辑删除。既有字段类型数据保持不变，不需要迁移。

## 14. 兼容性

- 历史确认承诺节点缺少 `scanAuditEnabled`，按 `false` 处理；
- 未启用扫描审核的节点不要求模板、扫描件、提示词或视觉服务配置；
- 现有文件上传节点、普通审核脚本和单文件替换语义不变；
- 历史 Submission 不补建视觉审核任务；
- 只有新发布且启用扫描审核的版本创建视觉任务；
- 现有模板资产克隆、删除和流程永久删除逻辑扩展到确认承诺模板，不改变对象键规则。

前端：

- `frontend/src/styles.css`：设置区、文件列表和教师结果样式。

后端：

- `backend/app/core/config.py`、`backend/.env.example`：视觉服务配置；
- `backend/app/core/database.py`：附件页数、顺序及迁移；

- 教师流程接口：受控读取评分结果与扫描件。

通用视觉审核程序的清单、参数定义、版本化处理器和必要测试代码放入现有 `backend/scripts` 和测试目录，不引入第二套队列、供应商 SDK 或前端状态库。

## 16. 验收标准

1. 未启用扫描审核的确认承诺节点行为不变。
2. 启用后，没有 DOCX 模板、审核模式或提示词时不能发布。
3. 学生未确认、未下载模板或没有有效扫描件时不能提交。
4. 学生可上传、下载、删除、替换和排序图片/PDF 混合材料。
5. 文件数、页数、单文件大小、总大小和格式限制由后端可靠执行。
6. PDF 所有页面与多张图片按稳定顺序进入同一 Chat 请求。
7. 通过/不通过模式严格校验 `passed/score/reason` 并向学生展示不通过原因。
8. 评分模式严格校验 0–100 分，节点直接通过，学生看不到分数和评分说明。
9. 教师能查看完整结果和全部扫描件入口。
10. 技术异常自动重试，最终失败可在保留扫描件的前提下重新审核。
11. 视觉服务通过通用环境变量配置，代码不写死豆包域名、Key 或模型。
12. API Key、原始模型响应和 Base64 页面不进入数据库、日志或前端。
13. 表单字段展开区不再出现字段类型二次选择器，其他字段设置保持可用。

## 17. 验证边界

实施阶段按项目约定不运行自动化测试、构建、浏览器或 Playwright。只更新测试代码，执行静态调用链、数据约束、差异范围和缓存清理审计，并以非 Docker 方式重启 FastAPI 与 Vite。完整上传、PDF 多页、模型返回、权限可见性与错误重试由用户按验收标准手动验证。
