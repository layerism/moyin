# 学生模板文件名上传校验设计

## 1. 目标

当文件上传节点配置了教师模板时，学生只能上传与模板同名的文件。校验在文件上传阶段完成，而不是在节点提交或自动审核阶段完成，以便学生在误传时立即得到提示。

本设计用于降低误上传其他文档的概率，不实现文档内容、哈希或结构指纹比对。

## 2. 业务规则

1. 仅对已绑定模板的文件上传节点启用文件名校验。
2. 学生上传文件的主文件名必须与教师模板完全一致；扩展名比较忽略大小写。
3. 比较前对文件名执行以下规范化：
   - 去除客户端可能携带的路径，仅保留文件名；
   - 转换为 Unicode NFC；
   - 去除文件名前后的空白字符；
   - 主文件名保持大小写敏感；
   - 扩展名转换为小写后比较。
4. 文件名不一致时，上传接口立即拒绝请求，并返回：

   `文件名与模板不一致，请将文件重命名为“<模板文件名>”后重新上传。`

5. 校验失败时：
   - 不向 OSS 写入新对象；
   - 不新增或更新 `uploaded_files`；
   - 不删除学生此前尚未提交的已上传文件；
   - 不改变草稿、节点状态或审核状态。
6. 校验成功时，后端使用模板的权威原始文件名：
   - 生成 OSS 对象键中的可读文件名部分；
   - 写入 `uploaded_files.original_name`；
   - 返回给前端并写入学生草稿；
   - 用于提交快照、审核脚本文件名和下载展示。
7. 文件内容、大小、SHA-256 和内容类型仍以学生实际上传文件为准。
8. 未配置模板的文件节点保持现有上传和命名逻辑。
9. 已提交的历史文件不追溯校验或重命名。

## 3. 上传数据流

```text
学生选择文件
  -> 后端取得节点上传上下文与当前模板元数据
  -> 规范化并比较学生文件名和模板文件名
  -> 不一致：返回 422，终止上传
  -> 一致：执行现有扩展名、大小和节点权限校验
  -> 使用模板文件名生成 OSS 对象键并上传
  -> 保存学生实际文件元数据，但 original_name 固定为模板文件名
  -> 成功后删除该学生此前尚未提交的旧 OSS 对象
```

文件名校验必须发生在计算完整文件哈希和写入 OSS 之前。现有权限、名单、节点开放时间、模板下载记录、文件类型和大小校验继续保留。

## 4. 后端边界

`FileUploadContext` 增加可选模板元数据，至少包含模板资产 ID 和原始文件名。模板信息必须由发布版本绑定关系和 `flow_template_assets` 查询得到，不接受客户端传入模板名称。

上传路由负责：

- 清理客户端文件路径；
- 调用共享文件名规范化与比较函数；
- 在不匹配时返回 422；
- 匹配时将模板原始文件名作为后续权威名称。

文件仓储层继续保存调用方传入的权威 `original_name`，无需数据库迁移。

## 5. 前端行为

沿用现有上传接口。收到 422 后使用浏览器原生警告弹窗显示后端返回的完整提示，不再把上传错误写入弹窗背后的页面横幅。关闭警告后，上传区域恢复为可选择状态，当前草稿中已有文件保持不变。

本次不增加文件内容检测进度、自定义二次确认弹窗或自动修改学生本地文件名。

## 6. 边界情况

- 模板 `A.docx` 与学生文件 `A.DOCX`：通过，服务端名称统一为 `A.docx`。
- 模板 `A.docx` 与学生文件 `a.docx`：拒绝。
- 模板 `A.docx` 与学生文件 `A .docx`：拒绝。
- 模板中文名称采用不同 Unicode 组合形式但视觉相同：NFC 后通过。
- 学生文件名包含伪造目录：只比较清理后的末级文件名。
- 模板元数据缺失或发布绑定异常：拒绝上传并返回服务端配置错误，不回退为无模板上传。

## 7. 安全与能力边界

文件名一致性只能防止普通误传。学生仍可将无关文件主动重命名为模板名称，因此该规则不能证明文件来源于模板，也不能替代后续审核脚本。

## 8. 验收标准

1. 有模板节点上传不同文件名时，在上传阶段立即收到明确提示，OSS 和数据库均不产生新记录。
2. 学生将文件改为模板名称后可正常上传。
3. 上传成功后的草稿、提交记录、审核输入和下载展示均使用模板文件名。
4. 校验失败不会覆盖或删除学生此前尚未提交的文件。
5. 无模板节点与历史已提交文件行为不变。
