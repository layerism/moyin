# 学生名单单人录入与关闭核对设计

## 1. 目标

在教务流程的“学生名单”弹窗中增加单个学生录入能力，并在本次打开弹窗期间发生任何名单变更后，要求教师完成一次明确的关闭核对，避免通过关闭按钮或遮罩直接退出而未检查名单结果。

## 2. 现状

当前名单弹窗已经具备：

- Excel、CSV 文件解析和导入预览；
- 批量导入后立即写入服务器；
- 名单搜索、有效与已移除数量展示；
- 单条学生权限移除及行内二次确认；
- 点击右上角关闭按钮或外部遮罩直接关闭。

现有 `POST /api/workflows/{flow_id}/roster/import` 接受任意数量的姓名、学号记录，并已统一处理新增、姓名更新和已移除学生恢复。因此，单人录入可以复用该接口，不需要增加后端路由、数据库表或持久化规则。

## 3. 方案选择

采用“服务器即时保存，关闭时人工核对”的最小闭环：

- Excel 导入、单人录入和移除学生继续在操作成功时立即保存；
- 前端记录本次弹窗会话是否发生过成功的名单变更；
- 有变更时关闭需要教师明确确认；
- 无变更时保持直接关闭。

不采用浏览器内批量暂存后统一提交，因为这会引入撤销、并发覆盖和页面关闭丢失等额外状态；不新增单人录入专用接口，因为现有批量接口已完整覆盖相同业务规则。

## 4. 单人录入

在批量导入区下方增加紧凑的“单个录入”区域，包含：

- 学号输入框；
- 姓名输入框；
- “添加学生”按钮。

交互规则：

1. 姓名或学号仅包含空白或为空时，按钮禁用；
2. 提交时对姓名和学号执行首尾空白清理；
3. 调用现有 `workflowApi.importRoster()`，请求中只包含一条记录，`sourceFileName` 固定为“手动录入”；
4. 新学号新增为有效学生；
5. 已移除学号恢复为有效学生；
6. 已存在学号但姓名不同，沿用现有导入语义更新姓名；
7. 成功后更新完整名单、有效人数和父级人数，清空两个输入框；
8. 成功提示根据服务器汇总结果显示“已添加”“已恢复”或“已更新”；
9. 失败时保留输入内容并显示现有错误提示，便于教师修正后重试。

Excel 文件选择、解析预览和批量导入行为保持不变。

## 5. 名单变更与关闭核对

`FlowRosterDialog` 增加两个本地状态：

- `hasRosterChanges`：本次弹窗会话是否成功执行过批量导入、单人录入或学生移除；
- `confirmingClose`：是否正在显示关闭核对提示。

状态规则：

- 初次打开弹窗时两个状态均为假；
- 批量导入、单人录入或移除请求成功后，将 `hasRosterChanges` 设为真；
- 失败请求不改变 `hasRosterChanges`；
- 查询、搜索、选择或解析文件不属于名单变更；
- 请求进行中禁止发起关闭，避免服务器结果与关闭动作竞态。

所有关闭入口共用 `requestClose()`：

- `busy` 为真：忽略关闭动作；
- `hasRosterChanges` 为假：直接调用父级 `onClose()`；
- `hasRosterChanges` 为真：显示关闭核对提示，不关闭弹窗。

关闭核对提示位于名单弹窗内部，文案为“名单变更已保存，请确认是否完成核对”，提供：

1. “继续核对”：关闭提示，保留名单弹窗；
2. “确认关闭”：调用父级 `onClose()`。

右上角关闭按钮和外部遮罩均调用 `requestClose()`，保证行为一致。核对提示显示期间不允许通过再次点击遮罩绕过确认。

## 6. 错误与并发边界

- 批量导入、单人录入和移除继续共用既有 `busy` 请求锁，禁止重复提交；
- 单人录入失败不清空字段；
- 名单变更已经服务器保存，关闭核对只表达“教师完成核对”，不提供撤销语义；
- 关闭提示不会声称尚未保存，避免教师误以为“继续核对”会影响持久化；
- 不修改名单访问控制、学生身份匹配或发布前有效名单校验。

## 7. 文件范围

预计修改：

- `frontend/src/features/academic-flow/FlowRosterDialog.tsx`
- `frontend/src/styles.css`
- `backend/tests/test_flow_roster.py`

后端业务代码与前端 API 无需修改。后端测试仅补充单条记录复用导入接口时的新增、更新和恢复语义断言。

## 8. 验收标准

1. 教师可以输入学号和姓名添加单个学生；
2. 单人录入成功后名单、数量和父级“学生名单”人数立即更新；
3. 单人录入已有学号时沿用现有更新或恢复语义；
4. 单人录入失败时输入内容不丢失；
5. 批量导入、单人录入或移除成功后，点击关闭按钮或遮罩均出现关闭核对；
6. “继续核对”保留弹窗，“确认关闭”才退出；
7. 未发生名单变更时仍可直接关闭；
8. 请求进行中不能关闭或重复提交；
9. 原有 Excel 导入、搜索和移除确认行为不受影响。

## 9. 验证边界

依据项目约定，实施时更新必要测试代码但不运行 pytest、前端测试、构建或浏览器自动化。仅进行静态业务逻辑审计：

- 三类成功变更是否统一设置 `hasRosterChanges`；
- 两个关闭入口是否统一经过 `requestClose()`；
- `busy` 是否覆盖新增提交与关闭动作；
- 单人录入是否复用既有接口和服务器汇总结果；
- 失败路径是否保留输入与弹窗状态；
- 是否未改变学生访问控制与发布校验。

完成静态审计后清理缓存，以本地方式重启 FastAPI 与 Vite，由用户手动验收。
