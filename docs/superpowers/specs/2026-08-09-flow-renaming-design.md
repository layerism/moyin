# 教务流程重命名设计

## 1. 目标

在教务流程列表中为教师提供明确、可发现的重命名入口。草稿和已发布流程均可重命名；名称变化只属于流程级元数据更新，不触发版本发布或学生运行数据迁移。

本次不修改流程结构、节点配置、发布版本、学生名单、分享链接或流程实例。

## 2. 业务规则

### 2.1 可重命名范围

- 当前教师拥有的未归档流程均可重命名；
- 草稿流程可以重命名；
- 已发布流程可以重命名；
- 已发布流程重命名后，教师端和学生端立即显示新名称，无需重新发布。

学生端运行时通过流程 ID 和发布版本关联，流程名称由 `flows.name` 实时读取。因此重命名不得改变：

- `flows.id`；
- 当前发布版本或历史版本；
- 分享令牌和分享链接；
- 学生名单；
- 已创建的学生流程实例；
- 节点状态、草稿、提交和审核记录。

### 2.2 名称校验

名称保存前执行以下规则：

1. 去除首尾空白；
2. 去除空白后不能为空；
3. 最长 120 个字符；
4. 新名称不能与当前名称相同；
5. 新名称不能与当前教师其他未归档流程重名。

前端用于即时反馈，后端必须在写事务内重新执行全部校验，前端校验不能作为一致性保证。

错误文案：

- 空名称或超过 120 个字符：`流程名称不能为空且不能超过 120 个字符`；
- 与当前名称相同：`新名称不能与当前流程名称相同`；
- 与其他有效流程重名：`已存在同名流程`；
- 流程不存在、已归档或不属于当前教师：沿用 404 `流程不存在`。

## 3. 后端接口与事务

新增专用接口：

```http
PATCH /api/workflows/{flow_id}/name
Content-Type: application/json

{"name": "新流程名称"}
```

请求模型只包含 `name: str`。仓储函数负责去除首尾空白并统一执行非空、长度、原名相同和名称唯一性校验，避免 Pydantic 在仓储自定义业务文案之前返回另一套错误格式。

建议仓储接口：

```python
def rename_flow(flow_id: str, name: str, teacher_id: int) -> dict[str, object]:
    ...
```

仓储事务执行顺序：

1. `BEGIN IMMEDIATE`；
2. 查询当前教师拥有且未归档的流程；
3. 校验新名称非空、不超过 120 字且不等于当前名称；
4. 查询当前教师其他未归档同名流程，查询条件排除当前 `flow_id`；
5. 更新 `flows.name` 和 `flows.updated_at`；
6. 写入 `audit_logs`，动作名为 `workflow_renamed`；
7. 事务提交后调用现有 `get_flow()` 返回完整流程数据。

审计日志：

```json
{
  "before": {"name": "旧名称"},
  "after": {"name": "新名称"}
}
```

不增加数据库字段、索引或迁移。现有“同一教师的未归档流程名称唯一”规则保持不变。

## 4. 前端数据流

在 `workflowApi` 增加：

```ts
renameFlow(serverId: string, name: string): Promise<ServerFlow>
```

`App.tsx` 向 `AcademicFlowView` 提供：

```ts
onRenameProcess(process: AcademicProcess, name: string): Promise<AcademicProcess>
```

调用成功后：

1. 将后端 `ServerFlow` 通过现有 `mapServerFlow()` 转换；
2. 仅替换 `academicProcesses` 中相同 ID 的流程；
3. 保留列表顺序，不将重命名流程移动到首位；
4. 关闭重命名弹窗；
5. 不重新获取整个流程列表。

后端返回的完整流程数据是成功后的权威状态，前端不得只做乐观字符串替换。

## 5. 列表交互

### 5.1 重命名入口

在每个流程列表项的操作区中，将重命名按钮放在“复制”和删除之间：

- 使用铅笔图标；
- `aria-label="重命名流程 <当前名称>"`；
- `title="重命名流程"`；
- 使用现有浅蓝操作语义，但视觉强度低于带文字的“复制”按钮；
- 点击按钮不得触发“进入流程”。

不使用双击名称、右键菜单或新的更多菜单。

### 5.2 重命名弹窗

复用现有 `NameDialog`：

- 标题：`重命名流程`；
- 占位文字：`请输入新的流程名称`；
- 输入框预填当前名称；
- 打开时聚焦并选中当前文本；
- Enter 确认；
- 取消或关闭不产生改动；
- 提交期间禁用关闭、取消和重复提交；
- 提交期间按钮显示“保存中”；
- 校验及后端错误显示在弹窗内部。

为保持通用弹窗复用，`NameDialog` 增加两个可选参数：

```ts
selectOnFocus?: boolean;
submittingLabel?: string;
```

重命名传入 `selectOnFocus` 和 `submittingLabel="保存中"`；创建流程等现有调用不传参数，继续保持当前默认行为与“创建中”文案。

前端提交前校验：

- 去除首尾空白；
- 空名称不提交；
- 超过 120 字不提交；
- 与当前名称相同不提交；
- 与列表内其他流程重名不提交。

## 6. 状态与错误处理

`AcademicFlowView` 增加独立的重命名状态：

- 当前目标流程；
- 输入值；
- 错误信息；
- 提交中状态。

重命名与创建、复制、删除弹窗互不共享提交状态，避免一个操作影响另一个操作。

接口失败时：

- 弹窗保持打开；
- 输入内容保持不变；
- 错误显示在弹窗内；
- 流程列表和学生端数据不作本地修改。

成功时才更新列表并关闭弹窗。

## 8. 验收标准

1. 每个流程列表项均有可访问的重命名按钮。
2. 点击按钮后弹窗预填当前名称并选中文本。
3. 草稿和已发布流程均可成功重命名。
4. 重命名不改变流程 ID、状态、发布版本、名单、分享链接或学生实例。
5. 已发布流程重命名后学生端立即显示新名称。
6. 成功后原列表位置不变，只更新目标流程数据。
7. 空名称、超长名称、原名相同和其他流程重名均被拒绝，并显示明确文案。
8. 后端在事务中校验所有权、归档状态和名称唯一性。
9. 成功重命名产生 `workflow_renamed` 审计日志，包含旧名称和新名称。
10. 接口失败时弹窗、输入和列表状态保持可恢复。

## 9. 验证边界

按项目约定，不运行自动化测试、构建或浏览器测试。实施完成后执行静态业务审计：

- PATCH 路由是否只接受名称；
- 仓储校验是否位于写事务内并排除当前流程；
- 更新是否仅涉及 `name` 与 `updated_at`；
- 审计日志是否记录旧名称和新名称；
- 前端是否以服务端完整响应替换同 ID 流程且保持顺序；
- 发布、版本、名单、链接和学生实例代码是否无改动；
- 弹窗提交状态和错误是否与其他流程操作隔离。

完成静态审计后清理项目源码缓存、重启本地 FastAPI 与 Vite 服务，并交由用户手动验收。
