# 名单驱动流程可见性与 DAG 版本迁移设计

## 目标

将学生可见流程、个人流程实例和流程版本迁移拆分为三个独立概念，并建立适用于任意有向无环图（DAG）的通用规则：

1. 学生登录后，直接看到其姓名和学号匹配的全部已发布 OA 流程，不依赖是否访问过分享链接。
2. 学生首次打开尚未开始的流程时，才幂等创建个人实例。
3. 教师重新发布流程后，全部既有实例切换到最新版本。
4. 未受修订影响的节点保留当前状态；受影响节点及其下游按新 DAG 重新计算。
5. 历史提交、附件和审核结果作为事实记录保留，不因版本迁移被删除。

本设计描述通用算法，不针对任何固定节点名称、固定连线形态或特定 OA 流程编写分支。

## 核心概念

### 流程授权

`flow_roster_entries` 表示学生是否有权发现和访问某个逻辑流程。授权由以下条件共同确定：

- 名单记录属于目标 `flow_id`；
- 名单记录状态为 `active`；
- 当前学生账号的 `student_no` 与名单学号精确匹配；
- 当前学生账号的 `name` 与名单姓名精确匹配；
- 流程状态为 `published`，且存在当前发布版本。

授权与 `flow_instances` 是否存在无关。分享令牌是邀请入口，不是授权来源。

### 逻辑流程、发布版本与个人实例

- `flows`：教师维护的逻辑 OA 流程。
- `flow_versions`：每次发布生成的不可变配置快照。
- `flow_instances`：某个学生在逻辑流程中的唯一运行实例。
- `node_instances`：个人实例中各稳定节点 ID 的当前运行状态。
- `submissions`：节点的不可变提交事实，可以跨版本保留多次记录。

同一学生在同一逻辑流程中只能有一个有效个人实例。实例在重新发布时原地迁移到最新 `flow_version_id`，不为每个版本创建新的并行实例。

## 数据模型调整

### 逻辑流程级实例唯一性

`flow_instances` 增加 `flow_id`，指向 `flows.id`，并建立：

```sql
UNIQUE(flow_id, student_account_id)
```

`flow_version_id` 继续表示实例当前运行的发布版本。创建和迁移实例时必须同时校验该版本属于同一个 `flow_id`，防止逻辑流程与版本引用不一致。

数据库迁移先从 `flow_versions` 回填 `flow_id`。若历史数据中同一学生、同一逻辑流程存在多个版本实例，则选择版本号最高、最近活动时间最新的实例作为规范实例，并将其他实例的节点提交、附件和审核历史归并到规范实例对应的稳定节点 ID。只有在历史数据完成归并并核对记录数量后，才删除空的重复实例外壳并建立唯一索引；不得只把重复实例快照写入审计日志后直接级联删除。

### 提交版本与失效信息

`submissions` 增加：

- `flow_version_id`：提交发生时的不可变版本；
- `invalidated_at`：因后续修订失效的时间；
- `invalidation_reasons`：结构化原因数组；
- `invalidated_by_version_id`：使本次提交失效的新版本。

现有提交通过其节点实例、流程实例和迁移前版本回填 `flow_version_id`。新提交必须直接写入实例当前版本，不依赖后续反向推断。

### 审核任务取消

`audit_jobs.status` 增加 `cancelled`。版本迁移将受影响提交对应的 `pending` 或 `running` 任务改为 `cancelled`。审核工作进程完成外部执行后，只有任务仍为 `running`、提交未失效且仍是节点当前尝试时才能更新提交和节点状态。

## 学生可见流程

对学生 \(s\)，其可见流程集合定义为：

$$
VisibleFlows(s)=\{f\mid f.status=published\land roster(f,s)=active\}
$$

学生流程中心以有效名单为查询起点，左连接个人实例，并返回逻辑流程级结果：

| 条件 | 展示状态 | 点击行为 |
| --- | --- | --- |
| 有有效名单，没有实例 | `not_started` | 创建最新版本实例并进入 |
| 有有效名单，实例进行中 | `in_progress` | 打开既有实例 |
| 有有效名单，实例已完成 | `completed` | 打开既有实例 |
| 无有效名单或名单已撤销 | 不展示 | 服务端拒绝进入和读取 |
| 流程未发布或已归档 | 不展示 | 服务端拒绝进入 |

每个逻辑流程只展示一条记录，不因存在多个历史版本而重复展示。

## 学生接口

### 查询可见流程

`GET /api/student/flows`

服务端从登录会话取得学生 ID，按账号姓名和学号查询有效名单及对应逻辑流程，不接受客户端传入学生标识。返回项至少包含：

```json
{
  "flowId": "logical-flow-id",
  "instanceId": null,
  "name": "流程名称",
  "status": "not_started",
  "publishedVersionId": "latest-version-id",
  "publishedVersionNo": 3,
  "lastActiveAt": null
}
```

已有实例时返回 `instanceId`、实例状态和最近访问时间。尚未开始时 `instanceId` 与 `lastActiveAt` 为 `null`。

### 进入逻辑流程

`POST /api/student/flows/{flowId}/enter`

该接口在单个事务中执行：

1. 读取当前登录学生账号。
2. 校验目标逻辑流程处于已发布状态。
3. 校验学生姓名、学号和有效名单。
4. 读取最新发布版本。
5. 若逻辑流程已有该学生的有效实例，返回既有实例。
6. 若不存在实例，按最新版本幂等创建实例及节点实例。

分享链接入口在完成令牌校验后复用同一进入服务，不再维护第二套实例创建规则。

## 通用 DAG 修订分析

设旧版本流程为：

$$
G_o=(V_o,E_o)
$$

新版本流程为：

$$
G_n=(V_n,E_n)
$$

节点 ID 是跨版本稳定标识。节点在画布中的位置、纯展示样式等非业务字段不参与运行状态失效判断；节点题目、类型、填写要求、文件限制、审核方式、审核脚本及参数等业务字段参与判断。

### 直接变化节点

定义：

$$
D=V_{added}\cup V_{changed}\cup V_{predecessor-changed}
$$

- \(V_{added}\)：新版本新增的节点。
- \(V_{changed}\)：节点 ID 不变，但业务配置快照发生变化的节点。
- \(V_{predecessor-changed}\)：节点 ID 不变，但直接前置节点集合发生变化的节点。

当前产品继续禁止删除已发布节点和已发布连线。若未来开放删除，必须独立设计历史节点归档及拓扑收缩规则，不在本设计中隐式处理。

### 失效传播

在新版本 DAG 中，从直接变化节点集合出发计算全部可达下游：

$$
I=D\cup Descendants_{G_n}(D)
$$

\(I\) 是需要重新计算当前运行状态的节点集合。未受影响集合为：

$$
U=(V_o\cap V_n)-I
$$

该算法统一处理串行、并行、分支、汇合及多级依赖，不针对具体节点名称或边组合写特例。

## 实例迁移规则

教师确认重新发布后，服务端在同一个数据库事务中创建新版本并迁移该逻辑流程的全部既有实例，包括当前已失去名单权限但仍需保留历史的实例。

### 未受影响节点

属于 \(U\) 的节点保留：

- `node_instance` 主键；
- 当前状态；
- `attempt_no`；
- 草稿；
- 提交、附件和审核结果；
- 学生个别截止时间覆盖；
- `opened_at`、`submitted_at`、`approved_at`。

未受影响节点已经 `approved` 时，在新版本中继续作为已满足的前置条件。

### 新增节点

新增节点创建新的 `node_instance`，初始状态不写死，而是按新 DAG 的前置状态计算：

- 无前置节点，或全部前置节点已经 `approved`：`available`；
- 存在未通过的前置节点：`locked`；
- 本应开放但新版本有效截止时间已过：`expired`。

### 配置改变、前置改变及受影响下游

对 \(I\) 中已经存在的节点：

1. 保留原 `node_instance` 和 `attempt_no`。
2. 保留全部历史 `submissions`、审核任务结果和已提交附件。
3. 将旧提交标记为因版本修订失效，记录来源版本、目标版本、失效时间和原因。
4. 清除当前运行态的 `submitted_at` 与 `approved_at`。
5. 删除不完整草稿及尚未提交的临时附件；删除前写入必要审计快照。
6. 取消尚未完成的旧版本审核任务；审核工作进程在落库前再次校验提交是否仍属于当前有效尝试。
7. 清除该受影响节点的学生个别截止时间覆盖，改用新版本节点截止时间；原覆盖写入审计记录。
8. 按新 DAG 重新计算 `available`、`locked` 或 `expired`。

失效原因使用结构化枚举：

- `node_definition_changed`：节点业务配置改变；
- `predecessors_changed`：直接前置集合改变；
- `upstream_invalidated`：上游变化传播到该节点。

同一节点可能同时记录多个原因。

### 拓扑顺序重算

所有新增或失效节点按照新 DAG 的拓扑顺序计算。对任意节点 \(v\)，统一使用：

$$
ready(v)=\bigwedge_{p\in Pred_{G_n}(v)} status(p)=approved
$$

- `ready(v)` 为真时，节点进入 `available`，但仍需检查截止时间。
- `ready(v)` 为假时，节点进入 `locked`。
- 空前置集合的合取结果为真，因此根节点可以直接开放。

运行期间某个节点重新通过后，现有下游推进服务必须复用同一个 `ready` 判定，避免发布迁移与日常节点推进产生不同结果。

### 流程实例状态

迁移结束后：

- 全部当前节点均为 `approved`：实例为 `completed`；
- 任一当前节点不是 `approved`：实例为 `in_progress`，清除 `completed_at`。

实例的 `flow_version_id` 更新为新发布版本。旧 `flow_versions` 保留为不可变历史，但不再作为当前学生运行版本。

## 提交历史模型

当前实现会删除失效节点及其提交，只把快照写入审计日志。该行为不能满足历史保留要求，并可能级联删除附件元数据，必须改为原地迁移。

`submissions` 使用前述版本和失效字段区分“提交时所属版本”和“是否因后续修订失效”。

旧提交的业务审核状态继续保留，例如旧记录仍可显示为“当时已通过”；其版本有效性由上述失效字段单独表达，不能覆盖原审核结论。

新提交继续使用递增的 `attempt_no`。运行接口只把当前版本尚未失效的最新提交作为当前节点提交，同时可返回只读历史摘要。历史附件继续关联原 submission，不参与新尝试的文件校验。

## 并发与事务

重新发布必须在单个 `BEGIN IMMEDIATE` 事务中完成：

1. 校验教师所有权、预期当前版本和待发布配置哈希。
2. 验证 DAG 和节点业务配置。
3. 计算各来源版本到新配置的影响集合。
4. 创建新 `flow_version` 和运行配置。
5. 迁移全部规范实例及节点状态。
6. 将有效分享令牌重定向到新版本。
7. 禁用旧发布版本，更新逻辑流程当前状态。
8. 写入版本修订和迁移审计日志。

任一步骤失败时整体回滚，不允许出现流程版本已切换但部分学生仍停留旧版本的状态。

学生进入接口与重新发布事务都使用数据库写锁和唯一约束保证幂等。若学生进入与教师重新发布并发，后获得写锁的一方必须重新读取当前发布版本，最终实例只能指向最新发布版本。

## 安全与错误处理

- 所有学生接口从服务端会话取得学生身份。
- 客户端传入的学生 ID、学号、姓名和版本 ID 不参与授权。
- 名单外学生统一返回 `403`，不泄露流程名称、版本或其他名单成员。
- 未发布、已归档或不存在的流程统一按不可进入处理。
- 学生被移除后，既有实例和历史提交保留，但查询、进入、读取、暂存、上传和提交均被拒绝。
- 版本迁移中的内部差异和其他学生数量只向流程所有教师展示。

## 教师发布影响预览

重新发布确认框继续显示通用统计：

- 新增节点数；
- 内容改变节点数；
- 前置关系改变节点数；
- 需要重新提交的节点数；
- 受影响学生数。

“需要重新提交的节点”对应 \(I\) 中已有学生运行记录的节点。确认文案明确说明：历史提交会保留，但不再满足新版本要求，相关节点需要按新拓扑重新开放和提交。

## 验收规则

### 名单隔离

1. 每个 OA 流程维护独立名单。
2. 学生只看到其姓名和学号同时匹配的已发布流程。
3. 同一学生可同时看到多个授权流程。
4. 名单内但尚未开始的流程显示为 `not_started`。
5. 学生首次点击后创建最新版本实例，不要求先访问分享链接。
6. 名单外学生看不到流程，并且不能绕过列表接口直接进入。

### 任意 DAG 迁移

1. 单纯新增根节点时，原有无关分支状态保持不变。
2. 新增节点成为某既有节点的前置时，该既有节点及其全部下游失效并按新依赖锁定。
3. 修改任意节点业务配置时，该节点及其全部下游失效。
4. 只改变画布坐标或纯展示字段时，不使学生节点失效。
5. 并行分支中只有可达的受影响分支重算，另一分支保持原状态。
6. 汇合节点只有在新版本全部前置节点通过后才开放。
7. 多级下游按照拓扑顺序依次重新开放。
8. 迁移后全部既有实例指向最新发布版本。

### 历史完整性

1. 失效节点的旧提交、审核结果和已提交附件仍可按原版本追溯。
2. 历史审核结论不被改写，只额外记录版本失效事实。
3. 新提交使用新的 attempt，不能覆盖旧提交。
4. 未受影响节点的状态和提交不发生变化。
5. 迁移失败时版本、实例、节点和提交全部保持发布前状态。

## 非目标

- 不实现班级级、专业级或组织机构级授权。
- 不把名单跨流程复用或自动同步。
- 不允许学生自行搜索或申请加入未授权流程。
- 不开放已发布节点或连线删除。
- 不为每次发布复制一套并行学生实例。
- 不改变流程节点审核本身的业务规则。
