# 腾讯文档收集表简化版架构草案

## 需求定位

本项目不是通用网盘，也不是单纯的 DOCX 上传系统，而是构建“腾讯文档收集表”的简化实现。核心目标是让管理员像创建在线问卷或收集表一样，配置一个材料收集页面；填报用户打开链接后填写基础信息、上传指定材料，并提交到系统归档。

在标准收集表能力之外，系统增加一个专用能力：对用户上传的 `.docx` 文档执行 AI 格式检测、自动评语填写、批注生成和结果归档。该能力由管理员上传若干个 Python 脚本实现。平台负责任务编排、文件调度、脚本运行隔离、结果入库和 OSS 归档；具体检测规则、AI 调用逻辑和评语生成逻辑由脚本提供。

## 产品形态

系统参考腾讯文档收集表的基本交互，采用顶部导航、左侧题型栏、中间编辑画布和底部操作栏的页面结构。管理员主要在“编辑、统计、设置”三个工作区中完成配置、发布和查看。

| 工作区 | 作用 |
| --- | --- |
| 编辑 | 创建收集表，添加题目，配置上传材料项，配置 AI 检查脚本 |
| 统计 | 查看提交人数、提交明细、文件状态、检查结果、导出数据 |
| 设置 | 配置学生名单、截止时间、文件自动命名规则 |

### 管理员编辑页

编辑页对标腾讯文档收集表的编辑界面：

1. 顶部栏显示收集表名称、保存状态和全局菜单。
2. 顶部页签提供“编辑、统计、设置”切换。
3. 左侧为题型面板，包含基础题型、高级题型和常用题库。
4. 中间为收集表画布，展示标题、描述、名单入口、题目卡片和 AI 辅助入口。
5. 底部固定“预览”和“发布”按钮。

管理员在编辑页中完成题目设计、文件题配置、AI 脚本绑定和发布前预览。

### 管理员设置页

设置页仍保持腾讯文档式顶部栏和页签结构，但内容收敛为本项目固定规则：

1. 截止时间。
2. 固定提交规则：仅学生名单内可填写；重复提交自动覆盖上一版。
3. 文件自动命名规则。
4. 学生名单：导入 Excel/CSV、下载模板、临时添加学生。

### 管理员统计页

统计页展示名单人数、临时添加人数、已提交人数、覆盖次数、未提交人数和检查失败数。列表支持按未提交、已提交、已覆盖、检查失败等状态筛选，并支持导出和批量提醒。

第一版不追求完整复刻腾讯文档，只实现收集表闭环和 DOCX AI 增强能力。

## 用户角色

| 角色 | 主要能力 |
| --- | --- |
| 管理员 | 创建收集表、配置题目、配置 DOCX 上传项、上传 Python 脚本、查看统计结果 |
| 填报用户 | 打开收集表链接，填写基础信息，上传 DOCX 文档，查看提交和检查状态 |
| 审核人员 | 查看提交记录，下载原始文档、批注文档和检查报告，标记审核状态 |

## 收集表题型

第一版支持最小但完整的题型集合：

| 题型 | 用途 | 是否必需 |
| --- | --- | --- |
| 单行文本 | 姓名、学号、班级、手机号等短文本 | 是 |
| 多行文本 | 备注、说明、补充材料说明 | 可选 |
| 单选题 | 固定分类选择 | 可选 |
| 多选题 | 多标签或多项选择 | 可选 |
| 日期题 | 提交日期、材料时间 | 可选 |
| 文件题 | 上传 DOCX 材料 | 是 |

文件题是本项目的关键题型。管理员可以为每个文件题配置：

1. 文件名称，例如“毕业论文正文”“实习材料”“课程设计报告”。
2. 是否必传。
3. 文件数量上限。
4. 文件大小上限。
5. 允许的文件类型，第一版限定为 `.docx`。
6. 绑定的 AI 检查脚本集合。
7. 文件自动命名规则，例如“学号-姓名-材料名称.docx”。

## 核心功能边界

第一版需要完成以下闭环：

1. 管理员创建一个收集表。
2. 管理员导入学生名单，必要时临时添加学生。
3. 管理员添加基础题目和若干 DOCX 文件题。
4. 管理员为文件题设置自动命名规则。
5. 管理员上传一个或多个 Python 脚本，并绑定到指定文件题。
6. 管理员发布收集表，生成可访问链接。
7. 只有学生名单内的姓名和学号匹配者可以填写。
8. 同一学生重复提交时覆盖上一版提交，不生成多条并列提交记录。
9. 填报用户填写必填项并上传必需 DOCX 文档。
10. 系统在前端和后端同时校验名单、必填项、文件类型、文件数量和文件大小。
11. 校验通过后保存或覆盖提交记录。
12. 系统按自动命名规则重命名上传文件，并将原始 DOCX 上传到阿里云 OSS。
13. 系统异步运行绑定的 Python 脚本，执行 AI 格式检测和自动评语填写。
14. 系统保存检查结果 JSON、带批注 DOCX、自动评语和运行日志。
15. 管理员在统计页查看提交状态、检查状态和审核状态。
16. 审核人员下载原始文档、批注文档和检查报告。

## 非目标

第一版暂不实现以下功能：

1. 多人实时协同编辑收集表。
2. 类似在线 Word 的正文编辑器。
3. 通用文件格式检查。
4. 任意脚本无约束运行。
5. 复杂工作流审批引擎。
6. 完整 AI Agent 平台。

## 核心模块

| 模块 | 职责 |
| --- | --- |
| 认证与权限 | 登录、角色区分、收集表访问控制 |
| 收集表编辑器 | 管理题目、分组、必填规则、文件题配置 |
| 发布与填写 | 生成填写链接，渲染收集表，处理用户提交 |
| 学生名单 | 导入名单、临时添加学生、校验姓名和学号 |
| 提交校验 | 校验名单、必填项、字段格式、文件数量、文件类型和大小 |
| 文件归档 | 将原始文档、批注文档和报告归档到阿里云 OSS |
| 文件命名 | 按管理员配置的规则自动重命名上传文件 |
| 脚本管理 | 上传、版本化、校验和启停 Python 脚本 |
| AI DOCX 检查 | 编排脚本运行，执行格式检测、评语填写和批注生成 |
| 统计与审核 | 展示提交明细、检查结果、审核状态和导出数据 |

## 数据流

### 收集表创建流程

1. 管理员新建收集表。
2. 管理员配置标题、说明和截止时间。
3. 管理员导入学生名单，必要时临时添加学生。
4. 管理员添加基础题目和 DOCX 文件题。
5. 管理员为文件题配置自动命名规则。
6. 管理员上传 Python 脚本，并将脚本绑定到指定 DOCX 文件题。
7. 系统校验脚本输入输出协议。
8. 管理员发布收集表。

### 用户提交流程

1. 用户打开收集表链接。
2. 前端根据表单 schema 渲染题目。
3. 用户填写姓名和学号。
4. 系统校验用户是否在学生名单内。
5. 用户填写基础信息并上传 DOCX。
6. 前端执行必填和文件规则校验。
7. 后端再次校验名单、表单 schema 与上传文件。
8. 后端按文件自动命名规则重命名文件。
9. 后端保存提交记录；若该学生已有提交，则覆盖上一版。
10. 后端上传原始 DOCX 到阿里云 OSS。
11. 后端创建 AI DOCX 检查任务。
12. Worker 领取检查任务，下载原始 DOCX，运行绑定脚本。
13. Worker 上传批注文档、评语结果和检查报告。
14. 系统更新提交状态和统计结果。

## AI DOCX 检查与自动评语填写

AI DOCX 能力由若干 Python 脚本组合实现。脚本可以完成以下任务：

1. 读取 DOCX，检查标题、字体、字号、段落、页边距、页眉页脚、表格格式等规则。
2. 调用指定 AI 模型，对正文内容、摘要、结论、格式说明等进行评估。
3. 根据检测结果生成自动评语。
4. 将评语写入 DOCX 指定位置，或以批注、修订痕迹、附录形式写入。
5. 输出结构化 JSON，供统计页展示。

### 脚本绑定方式

一个 DOCX 文件题可以绑定多个脚本。脚本按顺序执行：

```text
原始 DOCX
  -> 脚本 A：基础格式检测
  -> 脚本 B：AI 内容评估
  -> 脚本 C：自动评语填写
  -> 批注文档 + 检查报告
```

每个脚本应声明：

| 字段 | 说明 |
| --- | --- |
| `name` | 脚本名称 |
| `version` | 脚本版本 |
| `entrypoint` | 入口文件 |
| `required_env` | 需要的环境变量，例如 AI API Key |
| `input_contract` | 输入文件和元数据约定 |
| `output_contract` | 输出 DOCX、JSON 和日志约定 |
| `timeout_seconds` | 最大运行时间 |

### 脚本输入

平台向脚本提供统一输入：

| 参数 | 含义 |
| --- | --- |
| `input_docx` | 当前待处理 DOCX 文件路径 |
| `output_docx` | 当前脚本输出 DOCX 文件路径 |
| `output_json` | 当前脚本输出 JSON 文件路径 |
| `metadata_json` | 收集表、题目、提交用户和脚本配置 |
| `workdir` | 当前脚本可读写工作目录 |

### 脚本输出

每个脚本至少输出一个 JSON 文件。需要修改或批注文档时，同时输出 DOCX。

```json
{
  "passed": false,
  "summary": "文档存在格式问题，已生成修改建议。",
  "comments": [
    {
      "target": "第 1 页标题",
      "comment": "标题字号应调整为三号黑体。"
    }
  ],
  "issues": [
    {
      "code": "title_font_size_error",
      "level": "warning",
      "location": "第 1 页标题",
      "message": "标题字号不符合要求",
      "suggestion": "建议改为三号黑体"
    }
  ],
  "artifacts": {
    "output_docx": "output.docx"
  }
}
```

## 脚本安全边界

用户上传的 Python 脚本必须运行在隔离环境中：

1. 默认禁止访问业务数据库。
2. 默认禁止访问任务目录之外的文件。
3. 默认禁止访问内网服务。
4. 限制运行时间、内存、CPU 和输出文件大小。
5. AI API Key 通过受控环境变量注入，不写入脚本文档。
6. 脚本运行失败时，不影响原始提交归档，只将检查状态标记为失败。
7. 每次运行保留脚本版本、输入文件 hash、输出文件 hash 和错误日志。

## 状态要求

系统至少需要区分以下状态，便于用户和管理员判断进度：

| 对象 | 状态 |
| --- | --- |
| 收集表 | 草稿、已发布、已关闭 |
| 用户提交 | 未提交、已提交、已覆盖、已退回、已通过 |
| 文件检查 | 待检查、检查中、检查成功、检查失败 |
| 审核 | 待审核、通过、退回 |

状态设计先服务产品理解，后续再映射到具体数据库字段。

## 待确认问题

1. 填报用户是否必须登录，还是只校验名单中的姓名和学号。
2. 退回后是覆盖原提交，还是保留退回前版本用于审计。
3. 文件自动命名规则需要支持哪些变量，例如学号、姓名、班级、材料名称、提交时间。
4. AI 脚本由管理员上传，还是由系统预置后管理员选择。
5. AI 脚本是否允许联网调用外部模型。
6. 批注文档是否必须保持原 DOCX 格式完全不变。
7. 统计页是否需要按班级、专业、任务批次等维度筛选。

## 后续设计顺序

后续不应先进入数据库字段实现，建议按以下顺序推进：

1. 固化页面与用户流程。
2. 固化收集表题型和文件题规则。
3. 固化 AI 脚本输入输出协议。
4. 固化状态流转与异常处理。
5. 再设计数据库表、接口和文件存储路径。
